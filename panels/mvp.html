MVP Plan

FORGE is built in three maturity rungs, not three different products. The same application — data locked, methodology exposed — is carried up a ladder: first proven locally, then deployed, then opened to an LLM agent. The science underneath all three is identical, so the project always has a complete deliverable no matter how high the ladder is climbed.

Acronyms are decoded on hover throughout this page (look for the dotted underline). A full acronym glossary sits at the bottom of the page.

The three rungs

Phase 1 — local + logging

Weeks 2–5

Fully functional full stack on localhost via docker compose: FastAPI backend, the LLLA + HMC worker, the knob panel, the calibration tier, and a resource-logging layer that records memory and time per run. This rung is also the instrument the experiments run on.

MVP — deployed

Weeks 6–7

Identical behaviour to Phase 1, fully deployed. The same Docker images run on the cloud host; the static frontend on GitHub Pages points at the deployed API. The only thing that changes between local and deployed is one environment variable.

Stretch — + MCP

Weeks 8–9

The same backend, exposed a third way: an MCP server that advertises the compute functions as tools an LLM (e.g. Claude Desktop) can call. No new infrastructure — a thin manifest file that forwards to the endpoints already built in Phases 1–2.

Architecture: one backend, three front doors, two compute paths

Every rung reuses a single backend. What changes is who calls it and which hardware runs the heavy work. The interactive path (LLLA) is closed-form and must be instant, so it lives on an always-on CPU box; the heavy path (HMC/NUTS) runs for minutes and benefits from a GPU, so it runs serverless and scales to zero — paying only while a job runs.

Hosting & cost

Target budget: ~$25/month. That figure is the size of one always-on CPU box, which is the only component that must run continuously. A warm GPU is deliberately excluded — dedicated GPU machines start near $100/month and a warm card runs $300+/month, so the heavy path is serverless and effectively $0 at idle. Resource-logging feature (Phase 1)

Phase 1 ships a logging layer whose purpose is to turn Phase 2's infrastructure sizing into an empirical question instead of a guess. As each model and Bayesian-library run executes, a @profile_run wrapper records per-run telemetry; fitting a simple model to that log predicts memory and cost at the larger Phase 2 scales before any bigger instance is paid for.

Recorded per runWhy
run type (LLLA / HMC), config knobs, n_samples / n_chainsthe independent variables of the cost model
dataset id + size, parameter countscale inputs to extrapolate from
peak resident memory (RSS)decides which instance tier is needed
wall-clock time, CPU time× host $/hr → per-job cost (esp. serverless GPU)
timestamp, tier/hostprovenance; separates local vs deployed runs

One implementation note that matters: memory is measured as true process peak RSS, sampled on a background thread (e.g. psutil), not with tracemalloc. JAX/XLA and PyTorch allocate tensors outside the Python heap, so a heap-only tool would undercount badly. The log is appended as JSONL (or a small SQLite table). Its output — fitted curves of mem ≈ f(n_params, n_samples, data_size) and time ≈ f(·) — becomes both the Phase 2 budget justification and a figure in the write-up.

Schedule

The schedule follows the course phases — introduction, planning, design/implementation, testing, paper, hand-in. The substantive work is standing up the three reproduction projects — genre recognition, phonon DOS, and the ATLAS long-lived-particle search — inside the MVP phase-1 architecture in the software repo, each driven to functional ground-truth results before the next begins. Once all three are integrated (Week 5), the remaining implementation weeks layer Bayesian and visualization techniques across all three as needed. Risk & descope

Because the three reproductions are the core deliverable, getting all three running to ground-truth inside the phase-1 architecture (by Week 5) is the guaranteed floor — a complete capstone even if later work is trimmed. The Bayesian and visualization layer is the substantive middle; deployment and the MCP server remain stretch goals beyond it. If the testing weeks tighten, the descope order is the MCP stretch first, then the depth of the Bayesian/visualization refinements — never the three baseline reproductions or testing, which carry the write-up. Week 12 is a short Monday–Wednesday week, so final assembly must be substantially complete by the end of Week 11.
