Project Overview

FORGE is a web-hosted Bayesian posterior exploration tool. The dataset is locked; the methodology is open. What varies between users is how each chose to look at the data and reason about it — FORGE is the instrument that makes those choices visible, comparable, and replayable.

The acronym

FORGE — Functional-posterior Observatory for Refinement and Geometric Exploration. Reads as a noun phrase: "FORGE is a functional-posterior observatory…"

What the tool does

FORGE takes a locked benchmark dataset, exposes the modeling pipeline as user-controllable knobs (priors, architecture, hyperparameters, calibration targets), and lets a user fit a model, generate a posterior, and view it geometrically. The same dataset, fit by different users with different methodological choices, produces different posteriors — and FORGE surfaces those differences directly.

The thesis claim is: Bayesian methodology made explorable. Posterior shape is not just a number; it is an object that can be looked at, compared, and questioned.

User flow

  1. EDA layer. Explore the locked dataset before any model is fit. Feature distributions, missingness, pairwise correlations, subgroup structure. EDA outputs feed downstream prior and architecture decisions.
  2. Model selection. Pick the inference engine and architecture class. The first engine is a Bayesian neural network in the Hernández-Lobato lineage; further engines plug in behind the same interface.
  3. Knob panel. Set the priors, learning schedule, calibration targets, and other tunables. Every knob has a defensible default; deviations are recorded.
  4. Geometric posterior viewing. Fit completes, posterior is summarized as a geometric object the user can rotate, slice, and compare against the calibration tier.

Dataset tiers

FORGE is organized around four dataset tiers that anchor the calibration story:

TierRoleExample
C0 — Calibration Small, well-understood UCI-scale datasets where the right answer is known and posterior coverage can be measured UCI Boston, Concrete, Wine (Hernández-Lobato baseline triplet)
C1 — Demonstration A larger, public, harder benchmark where the tool's posterior-quality story shows up clearly FAIR Universe HiggsML
C2 — Benchmarked Hyperparameter sweeps and posterior-shape vs. knob-setting studies Internal sweep studies on calibration and demonstration tiers
C3 — Application Field-deployment demo on a real research dataset, contingent on advisor approval ATLAS MSVtx LLP search (provisional, pending Prof. Johns' approval)

Repository structure

The project lives across three repositories — not five — mapping cleanly to the three things being produced: a deployed application, research artifacts, and documentation.

RepositoryContents
INFO_698_documentation This site. Timeline, Gantt, proposal, mk-history, design diagrams, branding.
INFO_698_experiments Research code: Hernández-Lobato PoC, FAIR Universe HiggsML evaluation, hyperparameter sweeps, notebooks.
INFO_698_software The deployed application: frontend, backend, worker, calibration.

A stretch fourth repo (forge-mcp) is reserved for a Model Context Protocol server that exposes FORGE to LLM agents. This is post-MVP; the core proposal does not depend on it.

Architectural rule of thumb

Every backend endpoint is designed as if an LLM agent will be calling it: stateless or explicit-state, JSON in / JSON out, Pydantic-typed. This makes the deployed tool both human-usable today and agent-callable when the MCP stretch goal lands.
